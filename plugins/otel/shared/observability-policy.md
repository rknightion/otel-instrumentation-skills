# Observability policy
Retain telemetry by default. Optimise correctness, signal quality, correlation, queryability, runtime overhead, reliability and maintainability. Backend storage price and ingestion volume are not optimisation goals. Do not introduce SDK, probabilistic or tail sampling, arbitrary filters, dropped spans/logs/metrics or attribute removal to reduce cost. An explicit sampling/data-reduction request is a separate intentional decision: retrieve current mechanisms, explain loss and propagation effects, and validate the requested behavior. Existing sampling is evidence to report, not permission to silently change policy.

Cardinality depends on placement. Metric dimensions, Loki stream labels and operation grouping must remain bounded. Use route/templates for operation identity rather than object IDs or literal request URLs. Do not generate telemetry names from requests. User/request/session IDs, UUIDs and UIDs generally remain useful span attributes or structured log fields; they must not be promoted into metric dimensions or Loki labels. Normalize the grouping dimension while retaining useful original context in an appropriate non-indexed field. Hashing a UID does not bound its cardinality. Review resource-to-label promotion too. A manual span name does not automatically become a metric dimension: inspect the actual metric attribute path before claiming new series. Repeated instrumentation calls do not prove duplicate output if a library guards initialization; verify the boundary or emitted records. Query current Grafana documentation before claiming any normalization or label behavior. Verify queryability, index behavior and stream identity separately; being queryable does not prove a field is indexed.

Avoid duplicate automatic/manual telemetry and malformed or useless new instrumentation. Removing proven duplicates is a correctness change: explain the evidence and verify signal continuity, rather than applying broad noise filters. Do not aggressively redact PII as a generic optimisation. Never add capture of passwords, credentials, API keys or authentication tokens. Handle explicit sensitive-data requests using current authoritative guidance.

Guidance is vendor-neutral; Grafana Cloud is the usual backend. Resolve the actual destination from project configuration or the user before configuring exporters; never guess a staff stack or credential. No Dash0 products, endpoints, authentication, operator or derived attributes belong in implementations. Browser OTel instrumentation is intentionally excluded: Rob uses Grafana Faro. Route browser work to current Faro guidance outside this plugin. Dedicated application workflows cover Go, Python and JavaScript/TypeScript on Node only; do not invent Java, .NET or Ruby skills.
